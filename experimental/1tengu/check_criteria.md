# check_criteria.py - 評価項目形式チェッカー

## 概要

`check_criteria.py`は、Tengu Benchmark評価タスクの評価項目形式を自動検証するスクリプトです。data/ディレクトリ内の各Markdownファイルについて、評価項目が期待する形式に適合しているかをチェックします。

## 背景

### 課題

Shaberi評価フレームワークでFew-shot形式から構造化出力（JSONスキーマ）への移行を進める際、評価項目の形式統一が重要になります。120件のTengu Benchmarkタスクそれぞれについて、手動での形式確認は非効率的でエラーが発生しやすいという問題がありました。

### 期待する形式

評価項目は以下の形式に従う必要があります：

```markdown
[評価項目]
- 評価内容:点数点
- 評価内容:点数点
...

[評価するモデルの回答]
```

**階層構造もサポート：**
```markdown
[評価項目]
- 親項目の説明
  - 子項目の説明:点数点
  - 子項目の説明:点数点
- 通常項目:点数点
...

[評価するモデルの回答]
```

## 調査結果

### データセット概要

Tengu Benchmark（data/）の120件すべてのファイルを調査した結果、評価項目は以下の2つの形式パターンに分類されることが判明しました。

### 形式1: 単層構造（97件）

最も一般的な形式で、評価項目がフラットに並びます：

```markdown
[評価項目]
- 答えが867万円である:3点
- 全ての月の売り上げの合計を求めることで年平均売り上げ金額を求めている:2点
- 表の値を正しく読み取れている:2点
- 説明が具体的でわかりやすい:2点
- 自然な日本語である:1点

[評価するモデルの回答]
```

### 形式2: 階層構造（23件）

親項目の下に子項目がインデントされる形式：

```markdown
[評価項目]
- 文章中の以下の情報を含んでいる
  - 取引デジタルフォームの利用者の利益保護が目的の法律である:2点
  - 取引デジタルフォームの定義:2点
  - その他の関連用語の定義:2点
- 文章中の論理関係を保存している:2点
- 自然な日本語である:1点
- 要約として適切な短さである:1点

[評価するモデルの回答]
```

### 配点分析

#### 総配点の分布
- **10点満点**: 120件すべて
- **最頻配点**: 1点（自然な日本語）、2点（各種評価基準）
- **最高配点**: 4点（核心的な評価項目）

#### 項目数の分布
- **3-7項目**: 最も一般的
- **階層構造**: 通常3-5個の親項目、各親項目に1-4個の子項目

### 形式上の特徴

#### 共通パターン
1. **必須セクション**: `[評価項目]` → 評価項目リスト → 空行 → `[評価するモデルの回答]`
2. **点数表記**: すべて「X点」形式（「X pt」「X ポイント」等は使用されない）
3. **リスト記法**: マークダウンの`-`（ハイフン）を使用

#### 階層構造の仕様
- **インデント**: 2スペース固定
- **親項目**: 点数なし、説明のみ
- **子項目**: 必ず点数あり
- **混在**: 同一リスト内で階層項目と単層項目が混在可能

### 例外ケース（修正済み）

調査過程で発見され修正された問題：

#### ケース1: スペース不足（1件）
```markdown
-どちらが美味しいかの判断に有用な情報を含む:2点
# ハイフンの直後にスペースなし
```

#### ケース2: 複数空行（2件）
```markdown
[評価項目]
- 項目:1点


[評価するモデルの回答]
# 空行が2つ連続
```

### 仕様策定への影響

この調査結果に基づき、JSONスキーマ生成時には以下を考慮する必要があります：

1. **階層構造の統合**: 階層項目は「親項目：子項目」形式でスキーマに含める
   - 例: `"文章中の以下の情報を含んでいる：取引デジタルフォームの定義"`
2. **配点の自動抽出**: 正規表現`r':(\d+)点$'`で確実に抽出可能
3. **項目名の正規化**: 長い説明文をJSONキーとして使用する際の文字制限対応

## 検証ロジック

### 状態遷移モデル

スクリプトは4つの状態を持つ状態機械として動作します：

1. **search**: `[評価項目]`セクションを探索
2. **reading_criteria**: 通常の評価項目を読み取り
3. **checking_indent**: インデント階層の子項目を読み取り
4. **waiting_for_next**: 空行後の`[評価するモデルの回答]`を待機

### 形式パターン

#### 通常の評価項目
- **パターン**: `r'-.+:\d+点$'`
- **例**: `- 自然な日本語である:1点`

#### 階層の親項目
- **パターン**: `r'-.+$'`（末尾に点数なし）
- **例**: `- 文章中の以下の情報を含んでいる`

#### インデントされた子項目
- **パターン**: `r'  -.+:\d+点$'`（2スペースのインデント）
- **例**: `  - 取引デジタルフォームの定義:2点`

### アルゴリズムの特徴

#### 同一行再処理
状態変更時に`continue`を使用することで、同じ行を新しい状態で再評価します：

```python
elif re.match(r'-.+$', line):
    # 階層の親項目、インデント調査モードに移行
    state = 'checking_indent'
```

これにより、階層構造の親項目を適切に処理できます。

#### 柔軟な空行処理
複数の連続する空行にも対応し、最初の非空行が`[評価するモデルの回答]`であれば正常とみなします。

#### エラー早期検出
期待しない形式が見つかった時点で即座に`False`を返し、効率的な検証を実現します。

## 使用方法

### 実行コマンド
```bash
cd experimental
python check_criteria.py
```

### 前提条件
- `data/`ディレクトリが存在すること
- ディレクトリ内に`.md`ファイルが存在すること
- Python 3.6以上

### 出力例

**すべて正常な場合：**
```
結果: 120/120 件が正常
```

**エラーがある場合：**
```
✗ 021.md
✗ 081.md
✗ 096.md

結果: 117/120 件が正常
```

## 技術仕様

### 依存関係
- **標準ライブラリのみ**: `re`, `pathlib`
- **外部依存なし**: 追加インストール不要

### パフォーマンス
- **効率的な正規表現**: 複雑な文字列操作を回避
- **早期終了**: エラー検出時点で処理終了
- **メモリ効率**: ファイル単位での処理

### エラーハンドリング
- ファイル読み込みエラーの個別捕捉
- 処理継続（1件のエラーで全体が停止しない）
- 簡潔なエラーレポート

## 検出される問題例

### 1. スペース不足（修正済み）
```markdown
-評価項目:2点  # ハイフンの後にスペースなし
```

### 2. 複数空行（対応済み）
```markdown
[評価項目]
- 項目:1点


[評価するモデルの回答]  # 空行が2つ
```

### 3. 不正な階層構造
```markdown
[評価項目]
- 親項目
   - 子項目:1点  # インデントが3スペース（2スペース期待）
```

### 4. 不正な終了
```markdown
[評価項目]
- 項目:1点

[他のセクション]  # [評価するモデルの回答]以外
```
