# tengu-000-user.md から tengu-000-schema.json への変換手順

## 概要
評価タスクの指示文（`tengu-000-user.md`）から構造化出力用のJSONスキーマ（`tengu-000-schema.json`）を生成する手順を説明します。これにより、LLM-as-a-Judge手法の評価をより正確かつ効率的に実行できます。

## 入力ファイル: tengu-000-user.md

### ファイル構成
```markdown
[指示]
あなたは熟練した生成AIモデルの性能評価者です。評価項目に準拠して客観的に評価することで報酬を得ることができますが、評価項目と異なる評価をした場合報酬がもらえなくなってしまいます。
以下の質問,正解例,評価項目に基づいて評価するモデルの回答を0~10点の整数値で評価してください。

[質問]
「急がば回れ」という言葉について説明してください。

[正解例]
「急がば回れ」という言葉は、日本の諺の一つであり、直接的な意味は「急ぐときは、早道や危険な方法を選ばずに、むしろ回り道で確実で安全な道を通った方が結局は早く着けるものだ」というものです。この言葉は、物事は慌てずに着実に進めることが結果としてうまくいくという教訓を含んでいます

[評価項目]
- 本来の「急ぐときは、早道や危険な方法を選ばずに、むしろ回り道で確実で安全な道を通った方が結局は早く着ける」という意味について説明している:3点
- 一般化した「物事は慌てずに着実に進めることが結果としてうまくいく」という意味について説明している:3点
- ことわざであることを示している:2点
- 説明は具体的でわかりやすい:1点
- 自然な日本語である:1点
```

## 変換プロセス

### ステップ1: 評価項目の解析
入力ファイルの`[評価項目]`セクションから以下の情報を抽出：

| 評価項目 | 配点 |
|---------|------|
| 本来の「急ぐときは...」という意味について説明している | 3点 |
| 一般化した「物事は慌てずに...」という意味について説明している | 3点 |
| ことわざであることを示している | 2点 |
| 説明は具体的でわかりやすい | 1点 |
| 自然な日本語である | 1点 |
| **合計** | **10点** |

### ステップ2: JSONスキーマの基本構造設計

構造化出力のために、以下の基本構造を設計：

```json
{
  "type": "object",
  "properties": {
    "evaluation": {
      "type": "object",
      "properties": {
        // 各評価項目をここに配置
      }
    },
    "summary": {
      "type": "string",
      "description": "Overall assessment summary in Japanese of the model's answer"
    }
  },
  "required": ["evaluation", "summary"]
}
```

### ステップ3: 各評価項目のスキーマ変換

各評価項目を以下の構造に変換：

```json
"評価項目名": {
  "type": "object",
  "properties": {
    "points": {
      "type": "string",
      "enum": ["0", "配点に応じた値..."],
      "description": "Points assigned (0-X scale based on how well this criterion is met)"
    },
    "reasoning": {
      "type": "string",
      "description": "Brief explanation in Japanese of why this score was assigned"
    }
  },
  "required": ["points", "reasoning"]
}
```

### ステップ4: 配点に応じたenum値の設定

各評価項目の配点に基づいてenum配列を生成：

- **3点満点**の項目 → `["0", "1", "2", "3"]`
- **2点満点**の項目 → `["0", "1", "2"]`
- **1点満点**の項目 → `["0", "1"]`

### ステップ5: 設計上の重要な決定事項

#### 1. satisfiedフィールドを含めない理由
- 部分点（例：3点満点で2点）の場合、true/falseでは表現できない
- pointsフィールドのみで評価の度合いを十分に表現可能

#### 2. string型のenumを使用する理由
- integer型の`minimum`/`maximum`制約が一部のLLMで無視される可能性
- enumにより許可された値のみを確実に選択させられる
- 後処理で`parseInt()`により数値変換が容易

#### 3. total_scoreを含めない理由
- LLMによる計算エラーを完全に排除
- 各項目のpointsを後処理で合計する方が確実かつ効率的

#### 4. 言語指定の方法
- descriptionは英語で記述（国際標準）
- 実際の記入内容は"in Japanese"と明示的に指定

## 変換による改善点

### 1. 従来のFew-shot形式の問題点
- LLMが計算ミスをする可能性
- 出力フォーマットが不安定
- 評価の一貫性が保証されない
- Few-shot例の送信でトークンを浪費

### 2. 構造化出力による解決
- **計算の正確性**: 合計点は後処理で確実に計算
- **出力の安定性**: JSONスキーマによる厳密な形式保証
- **評価の一貫性**: enum制約により許可された値のみ選択可能
- **効率性**: Few-shot例が不要でトークン節約

## 実装時の後処理

生成されたJSON出力から合計点を計算する例（JavaScript）：

```javascript
function calculateTotalScore(evaluation) {
  let total = 0;
  for (const criterion in evaluation) {
    total += parseInt(evaluation[criterion].points);
  }
  return total;
}
```

## まとめ

`tengu-000-user.md`の評価指示文を`tengu-000-schema.json`のJSONスキーマに変換することで、より信頼性が高く効率的な評価システムを構築できます。この手法は他の評価タスクにも容易に適用可能で、大規模な評価プロジェクトにおいて特に有効です。
